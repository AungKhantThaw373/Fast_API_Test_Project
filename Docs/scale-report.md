# Phase 9 — scale report

This is the measured answer to one question: does Stillroom stay usable when a
manuscript is the size of a long serial? It is not a relevance claim. The
fixture is synthetic and its default vectors carry no meaning.

## Corpus

| Metric | Value |
|---|---:|
| Chapters | 1,100 |
| Words | 1,029,590 |
| Retrieval chunks | 6,600 |
| Arcs | 12 |
| Entities / aliases | 750 / 1,350 |
| Accepted facts | 100 |
| Threads | 70 |
| Synthetic import | 27.89 s (36,919.83 words/s), 0 failures |
| Database after import | 58 MB before the HNSW index; 92 MB after |

The corpus is generated by `scripts/generate_fixture.py`; it is not copied from
any published work. Import details are in `Docs/scale-import.md`. Chapter text
and synthetic 768-d vectors are written immediately; canon extraction is lazy
(P9-3), so opening the story does not trigger 1,100 AI calls.

## Read and save latency

Measured on the local machine against the scale database with Ollama
`nomic-embed-text:latest` warm, 30 requests per endpoint (10 for saves), and a
unique search query per request so the API cache does not turn the test into a
cache-hit benchmark. Values are milliseconds.

| Endpoint | p50 | p95 | max |
|---|---:|---:|---:|
| Story list | 6.2 | 7.1 | 9.0 |
| Story detail (1,100 chapters) | 41.0 | 112.5 | 117.5 |
| Chapter load | 5.0 | 8.3 | 8.7 |
| Hybrid search | 135.5 | 191.2 | 250.0 |
| Changed chapter save | 29.9 | 71.7 | 71.7 |

Search stages at p50: query embedding 69.6 ms, vector scan plus chunk load
20.2 ms, lexical 2.5 ms, name 1.7 ms, total 121.8 ms. The first search after
the embedding model has been evicted took about 4.7 s; that is a model-load
cost, not a query cost. The search p95 now meets the Phase 5 300 ms goal.

Raw reports: `Docs/eval/scale-api-hnsw.json` and
`Docs/eval/scale-api-exact.json`. The exact-scan run on the same 6,600 chunks
measured search p50 365.3 ms / p95 635.2 ms. The difference is the vector stage:
exact scan 179.0 ms p50 versus 20.2 ms with HNSW.

The changed-save number includes revision insert, reindex enqueue and the
audit/ledger work; it does not wait for the worker to re-embed the chapter. A
queued reindex is the correct behavior at this size: the save stays fast and
the worker catches up. The search cache is invalidated when the index version
changes, so a search immediately after a save may see the old chunk until the
worker finishes.

## HNSW decision

Phase 5 removed HNSW because the 10k benchmark did not justify it. That result
did not survive the 50k/100k tests. Exact filtered top-30 scans grew roughly
linearly; HNSW with `ef_search=400` and relaxed iterative scanning stayed at a
few milliseconds and recovered every exact neighbour in the clustered-vector
benchmark.

| Chunks | Exact p50 / p95 | HNSW ef400 p50 / p95 | Recall@30 | HNSW build | Index size |
|---:|---:|---:|---:|---:|---:|
| 10,000 | 26.3 / 56.7 ms | 3.0 / 4.2 ms | 1.0 | 14.3 s | 39.1 MB |
| 50,000 | 385.4 / 668.6 ms | 3.4 / 5.4 ms | 1.0 | 59.2 s | 195.3 MB |
| 100,000 | 1,460.4 / 1,598.1 ms | 2.2 / 4.8 ms | 1.0 | 112.2 s | 390.6 MB |

HNSW at `ef_search=200` returned 80% recall at 100k; 400 and 800 both returned
1.0 in this benchmark. The app uses 400. The index is global (all stories share
`story_chunks`), and the query sets `hnsw.iterative_scan=relaxed_order` so a
selective story or arc filter can keep filling the candidate list.

The migration is `f1b7c3d9e5a2_add_story_chunk_hnsw.py`. It creates
`ix_story_chunks_embedding_hnsw` and blocks writes while the index builds. The
benchmark build took 14.3 s at 10k chunks and 112.2 s at 100k; the 6,600-chunk
scale story migration completed too quickly to time meaningfully. The index
makes the chunk storage roughly 1.6× larger at 6,600 chunks
(69 MB chunk relations including TOAST, 26 MB HNSW) and about 2× larger at
100k.

This benchmark uses deterministic clustered vectors, not real prose. It proves
latency and candidate recall against a known ground truth; it does not prove
that real queries find better passages. `Docs/eval/hnsw-10k-50k-ef400.json` and
`Docs/eval/hnsw-100k.json` are the raw reports.

## What this does not prove

- **No relevance claim at 1M words.** The fixture vectors are synthetic. Real
  retrieval quality is still measured on the 12-chapter labelled set in
  `Docs/retrieval.md`.
- **A 30-minute mixed soak was run, not 24 hours.** It exercised search, story
  detail, chapter load, and repeated saves while the worker reindexed. The actual
  duration and latencies are in [phase-9-acceptance.md](phase-9-acceptance.md);
  do not describe it as a 24-hour soak.
- **Not a provider benchmark.** Search uses local Ollama embeddings. A cloud
  embedding model adds network latency that this report does not measure.
- **One machine.** 16 GB RAM, native PostgreSQL 18, no GPU. These numbers are
  not a capacity plan for other hardware.
- **No Docker run.** Docker is not installed in this environment; the Compose
  stack remains an unexecuted artifact.

## Reproduce

```powershell
# Scale database, API on 8001
$env:DBNAME = "stillroom_scale_test"
uv run uvicorn app.app:app --host 127.0.0.1 --port 8001

# Read/save measurements (Ollama must be running)
uv run --project backend python scripts/measure_scale_api.py --iterations 30 --save --save-iterations 10

# HNSW benchmark, disposable database
uv run --project backend python scripts/bench_hnsw.py --sizes 10000 50000 100000 --ef-search 200 400 800
```

`measure_scale_api.py` creates a temporary chapter for the changed-save test
and deletes it afterward. Delete any queued `reindex_chapter` jobs it leaves
before reusing the scale database.
